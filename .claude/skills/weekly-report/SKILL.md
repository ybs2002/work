# 주간보고서 작성

Git 커밋/PR 내역을 근거로, 팀장·동료가 1분 안에 읽을 수 있는 Markdown 주간보고서를 만든다.

## 1. 기간과 대상 확정

- 기본 기간: 이번 주 월요일 ~ 오늘. 사용자가 "지난주", 날짜 범위를 말하면 그에 맞춘다.
- 기본 작성자: `git config user.email`. 팀 전체 보고서를 원하면 작성자 필터를 뺀다.
- 원격 최신 내역을 반영하려면 먼저 `git fetch --all --prune`을 시도한다(실패해도 로컬로 진행).

## 2. 데이터 수집

번들 스크립트로 커밋·머지·변경 규모를 한 번에 뽑는다.

```bash
bash .claude/skills/weekly-report/scripts/collect_git.sh [since] [until] [author]
# 예: collect_git.sh 2026-09-21 2026-09-27 me@example.com
```

PR 정보가 필요하고 GitHub 도구(mcp__github__*)를 쓸 수 있으면 해당 기간에 작성/머지된 PR의 제목·번호·상태를 추가로 조회한다. 쓸 수 없으면 머지 커밋 메시지(`Merge pull request #N`)에서 PR 번호를 추출한다.

## 3. 분류와 요약

커밋을 하나씩 나열하지 말고 **작업 단위로 묶는다**. 보고서 독자는 커밋 해시가 아니라 "무엇이 끝났고 무엇이 남았는지"를 알고 싶어 하기 때문이다.

- 같은 브랜치·같은 기능·같은 티켓 번호(예: `ABC-123`)의 커밋은 한 항목으로 합친다.
- Conventional Commit 접두어로 성격을 판단한다: `feat` → 기능 개발, `fix` → 버그 수정, `refactor/perf` → 개선, `test/docs/chore/ci` → 기타.
- 머지된 것은 "완료", 머지 안 된 브랜치/열린 PR은 "진행 중"으로 본다.
- 커밋 메시지가 모호하면(`wip`, `fix`) 변경 파일(`git show --stat <hash>`)을 보고 내용을 추정해 쓴다.
- 차주 계획은 진행 중 항목, TODO 커밋, 열린 PR에서 추론하고, 근거가 약하면 `(확인 필요)`를 붙인다. 없는 일을 지어내지 않는다.

## 4. 출력 형식

아래 템플릿을 그대로 사용한다. 비어 있는 섹션은 "해당 없음"으로 남긴다.

```markdown
# 주간보고서 (YYYY.MM.DD ~ YYYY.MM.DD)

**작성자**: 이름 | **저장소**: repo-name

## 요약
- 이번 주 핵심 성과 2~3줄

## 금주 실적
### ✅ 완료
- [기능] 주문 API 페이징 적용 (#12)
### 🔄 진행 중
- [개선] 결제 모듈 리팩터링 — 70%, 테스트 보강 중 (#15)
### 🐛 버그 수정
- 회원가입 시 이메일 중복 검증 누락 수정 (#13)

## 차주 계획
- 결제 모듈 리팩터링 마무리 및 리뷰 반영

## 이슈 / 협조 요청
- 해당 없음

## 지표
- 커밋 N건 · PR 머지 N건 · 파일 N개 (+N / -N)
```

작성 원칙:
- 항목은 "무엇을 했다" 형태의 한 줄. 결과·효과가 있으면 덧붙인다.
- 내부 구현 용어보다 비즈니스/기능 관점 표현을 우선한다.
- PR 번호·티켓 번호는 괄호로 달아 추적 가능하게 한다.

## 5. 저장

기본 저장 경로는 `reports/weekly-YYYY-MM-DD.md`(기간 시작일 기준). 사용자가 다른 경로를 말하면 따른다. 저장 후 요약 섹션을 대화에도 보여준다.
